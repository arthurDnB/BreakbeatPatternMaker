# `patterns.txt` — wave-3 whole-pattern acceptance fixture

Plain-text record of **the frozen wave-3 contract**: for 47 cases the file stores the exact
`JSON.stringify(pattern)` bytes, their `sha256`, and the full settings knobs that produced them.
A native (C++/JUCE) port passes wave-3 acceptance only if it reproduces every `pattern` value in
this file byte for byte.

Generated by [`native/tests/generate-pattern-vectors.mjs`](../generate-pattern-vectors.mjs) from a
compiled `dist/` ESM snapshot. **Do not hand-edit `patterns.txt`** — regenerate it.

* 3 small human-readable examples (`source=synthetic`), plus
* 44 authoritative cases (`source=matrix`), each cross-checked against
  [`tests/fixtures/determinism-matrix.json`](../../../tests/fixtures/determinism-matrix.json)
  (the already-frozen F-DET matrix, defined in
  [`scripts/engine-determinism-fixture.mjs`](../../../scripts/engine-determinism-fixture.mjs)).

Current fixture: **655461 bytes, 991 lines, sha256 `da1ddd5945ca61cf744975925840b3e66b88dc671c3ee77ea59ea071fd59fb9d`**
(the generator prints the authoritative value; `sha256` here is over the LF byte form of the file).

## Line grammar

```
<name><TAB><value>
```

* A line whose first byte is `#` is a section header/comment; blank lines are skipped.
* Every other line has **exactly one raw TAB**, separating `name` from `value`.
  `value` never contains a raw TAB (TAB is escaped), so "split at the first TAB" is unambiguous.
* `name` is a `;`-separated list of `key=value` pairs. **The first field is always `kind`**;
  later fields must all contain `=` and their keys must be unique within the line.
* Lines are separated by `LF` (0x0A). The file currently contains no `CR`. A CRLF checkout
  (`core.autocrlf=true`) is still parseable because a trailing `\r` must be stripped before parsing
  (the existing parser already does this).
* The file contains **no** bytes outside `TAB`, `LF`, `0x20..0x7E` — every other byte is escaped.

## Escaping (`%XX`) — exact rules

### Encode (what the generator emitted)

1. Take the UTF-8 bytes of the text.
2. For each byte `b`, in order:
   * if `0x20 <= b <= 0x7E` **and** `b != 0x25` (`%`) **and** `b != 0x09` (TAB): emit `b` as one ASCII character;
   * otherwise: emit `%` followed by exactly two **UPPERCASE** hex digits.
3. Consequences: TAB → `%09`; `%` → `%25`; `0x7F` → `%7F`; every byte `>= 0x80` (including all
   UTF-8 continuation bytes) → `%XX`. Example in this file: `×` (U+00D7) → `%C3%97` inside one
   `reason` string.

### Decode (what a C++ reader must do)

1. Scan left to right.
2. If the current character is `%` **and** at least two more characters exist **and** both are hex
   digits (accept upper- **and** lower-case), consume all three characters and emit the single byte
   `16 * hi + lo`.
3. Otherwise emit the character's own byte (it is ASCII in a well-formed file).
4. The emitted byte sequence is the text; interpret it as UTF-8.

**Reuse the implementation you already have.** This is exactly the inverse of
`decodeField` in [`native/Source/core/SelfTest.cpp:53-69`](../../Source/core/SelfTest.cpp) — no new
code is needed for unescaping, and its lenient behaviour (a stray `%` not followed by two hex digits
is passed through literally) is acceptable because the generator never emits one.

The escaped form is **transport only**. `sha256` must be computed over the **decoded raw UTF-8
bytes**, never over the escaped text.

## Record kinds

| `kind` | extra name fields | `value` field |
|---|---|---|
| `contract` | `key=<name>` | pinned statement about the text contract |
| `jsnum` | `in=<JS numeric literal>` | expected ECMAScript `String(Number(in))` |
| `tolerance` | `quantity=<name>` | pinned audio-comparison tolerance (audio only) |
| `policy` | `key=<name>` | pinned comparison policy (audio only) |
| `case` | `id`, `source`, `frozen`, `axes`, `genre`, `algorithm`, `seed`, `engineVersion`, `ppq`, `eventCount` | expected `sha256` of the decoded `pattern` JSON (UTF-8 bytes) |
| `settings` | `case`, `knobs`, `sha256` | exact `JSON.stringify(settings)` text (escaped) |
| `setting` | `case`, `key`, `type`, `integer` / `size` / `index`+`etype` | one knob's value (containers: `type=array;size=count` then one `type=element;index=N` line per member) |
| `pattern` | `case`, `sha256`, `bytes` | exact `JSON.stringify(pattern)` text (escaped); `bytes` = UTF-8 length of the decoded text |

A case record is always the contiguous group `case` → `settings` → N × `setting` → `pattern`, all
sharing the same `case=` id. `source=matrix;frozen=yes` marks the 44 authoritative cases;
`source=synthetic;frozen=no` marks the 3 small examples.

`kind=jsnum` and all seven wave-3 kinds (`contract`, `tolerance`, `policy`, `case`, `settings`,
`setting`, `pattern`) are understood by the shipped self-test, so pointing the current binary at this
file must end in `PASS`:

```
native\build\bbpm_selftest.exe native\tests\vectors\patterns.txt
```

What those handlers check:

* Every decoded `pattern` / `settings` text is re-parsed and re-serialized by the port's own JSON
  writer; the round trip must reproduce the recorded text byte for byte (member order and ECMAScript
  number formatting included). The `sha256` must equal both the record's own digest and the `case`
  record's digest, and `bytes` must equal the decoded UTF-8 length.
* Inside a case group, `eventCount`, `ppq` and `engineVersion` from the `case` record must agree with
  the pattern JSON, `pattern.settings` must equal the `settings` record text, the number of
  **top-level** `setting` lines must equal `knobs` (`element` and `member` records are extra detail
  lines for nested values and are counted separately), every event must carry a non-empty `reason`,
  `layerOf` must be absent, and the top-level member order must be the engine's documented one.
* The prose records (`contract`, `tolerance`, `policy`) are validated as a **set**: every reviewed key
  exactly once, with non-empty text. `contract;key=numberFormat` additionally re-derives the four
  formatting facts it states. Prose is not machine-verifiable beyond that.

This proves the recorded evidence is canonical and internally consistent; it does **not** prove the
port generates the same patterns, because no generator is ported yet. The acceptance procedure below
is still what a future generator must satisfy.

## How to accept a native port against this file

1. Parse and unescape every line (rules above).
2. Build the settings object from the `settings` text (or from the `setting` knobs) for a case.
3. Serialize the ported generator's pattern with **your own** `JSON.stringify` equivalent, honouring
   member insertion order and ECMAScript number formatting (see the `contract` / `jsnum` records).
4. Compare the decoded `pattern` value **byte for byte** against your text; equivalently compare
   `sha256` of your UTF-8 bytes against the `sha256` field / `case` value.
5. Treat any difference as a failure with the case id and the first differing byte offset.
   There is **no tolerance** for this text.

Member order is genuinely part of the contract and differs per engine: the pattern object is
`engineVersion,settings,ppq,events` for `legacy-v1` and `engineVersion,ppq,settings,events` for
`groove-v2` and later. `reason` is inside the hashed text on purpose; `layerOf` is render-only
(`src/core/model.ts:116`) and must never be serialized.

## Regenerating

`node native/tests/generate-pattern-vectors.mjs` (run from the repository root; Node 22.15+/26).

| flag | effect |
|---|---|
| *(none)* | refresh `test-results/dist-snapshot/` from `dist/`, then write `native/tests/vectors/patterns.txt` |
| `--check` | re-derive everything and compare with the file on disk; **writes nothing**, exits non-zero on any difference |
| `--no-copy` | use the existing `test-results/dist-snapshot/` instead of re-copying `dist/` |
| `--dist-root <dir>` | read the compiled ESM from `<dir>` (mutually exclusive with `--no-copy`); `<dir>/core/generate.js` etc. |
| `--out <path>` | write somewhere else (used for scratch comparisons) |

The script refuses to run if any of the 44 matrix digest comparisons disagrees with
`tests/fixtures/determinism-matrix.json`, if the two internal runs produce different bytes, or if the
`dist` alias did not take effect (proven by module identity against the live `dist/`).

Native self-test invocation (explicit path, because the compiled-in default is
`vectors/random-model.txt`):

```
native\build\bbpm_selftest.exe native\tests\vectors\patterns.txt
```

`BBPM_VECTORS_PATH` only changes the *default* path; an explicit argument wins.

## Not frozen here (stated gaps)

* The 3 `source=synthetic` cases are pinned by **this file only** (their digests were produced and
  recorded in the same run that wrote them). They are illustrative; the 44 matrix cases are
  authoritative.
* The **pattern text** of the 44 matrix cases was not previously frozen anywhere — the matrix
  froze only digests. This file freezes the bytes now; their digests are cross-checked against the
  matrix on every run, so the bytes and the matrix cannot silently drift apart.
* Audio tolerances recorded in the `tolerance`/`policy` records come from
  `docs/NATIVE-PORT-PLAN.md:249-261` (table and policies from `docs/M1-RENDER-PLAN-CONTRACT.md:126-141`).
  They are duplicated here as data for convenience; the docs remain the source of truth.
* Cross-language float formatting outside these engines (e.g. `toFixed`, exponents with a leading
  zero) is **not** covered; only the formatting the engines actually emit is pinned, via the
  `contract`/`jsnum` records plus the whole-pattern texts.
